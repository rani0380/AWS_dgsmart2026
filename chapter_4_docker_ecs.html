1. 컨테이너가 중요한 이유

컨테이너는 애플리케이션과 실행 환경을 하나의 이미지로 패키징하여 어디서든 동일하게 실행할 수 있게 해준다. 기능경기에서는 Dockerfile 작성, ECR 이미지 Push, ECS/Fargate 배포, ALB 연결이 자주 출제된다.

Docker컨테이너 이미지 빌드와 실행
ECRAWS 컨테이너 이미지 저장소
ECSAWS 관리형 컨테이너 오케스트레이션
Fargate서버 관리 없는 컨테이너 실행 방식
컨테이너 배포 문제는 이미지, 포트, IAM Role, Security Group, Health Check를 순서대로 확인하면 대부분 해결할 수 있다.

4. Dockerfile 작성

Dockerfile은 이미지를 만드는 설계도이다. 기능경기에서는 간단한 웹 애플리케이션 또는 API 서버를 Dockerfile로 이미지화하는 문제가 자주 나온다.

FROM python:3.11-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8080
CMD ["python", "app.py"]
명령어의미
FROM베이스 이미지 지정
WORKDIR작업 디렉토리 지정
COPY파일 복사
RUN이미지 빌드 중 명령 실행
EXPOSE컨테이너가 사용하는 포트 문서화
CMD컨테이너 시작 시 실행 명령
EXPOSE는 실제 포트 공개가 아니다. Docker 실행 시 -p 옵션이나 ECS Task Definition의 portMappings가 필요하다.

5. Dockerfile Best Practice

latest 태그 지양node:latest보다 node:20-alpine처럼 명확한 버전 사용
경량 이미지 사용slim, alpine, distroless 활용
캐시 활용requirements.txt 또는 package.json을 먼저 복사
비root 실행USER appuser로 권한 최소화

Node.js 예시

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]

Multi-stage Build 예시

FROM golang:1.22-alpine AS builder
WORKDIR /src
COPY . .
RUN go build -o server

FROM alpine:3.19
COPY --from=builder /src/server /server
CMD ["/server"]
Multi-stage Build를 사용하면 빌드 도구가 최종 이미지에 포함되지 않아 이미지 크기와 공격 표면을 줄일 수 있다.

6. ECR 이미지 Push 흐름

ECR은 AWS에서 제공하는 컨테이너 이미지 저장소이다. ECS나 EKS에서 이미지를 실행하려면 먼저 ECR에 이미지를 Push해야 한다.

Dockerfile ↓ docker build Local Image ↓ docker tag ECR Repository ↓ ECS/EKS Pull Running Container
# ECR 로그인
aws ecr get-login-password --region ap-northeast-2 | \
  docker login --username AWS \
  --password-stdin ACCOUNT_ID.dkr.ecr.ap-northeast-2.amazonaws.com

# 이미지 빌드
docker build -t myapp:latest .

# 태그 지정
docker tag myapp:latest \
  ACCOUNT_ID.dkr.ecr.ap-northeast-2.amazonaws.com/myapp:latest

# Push
docker push ACCOUNT_ID.dkr.ecr.ap-northeast-2.amazonaws.com/myapp:latest
no basic auth credentials 오류는 ECR 로그인을 하지 않았거나 region/account/repository 주소가 틀린 경우가 많다.

7. ECS 핵심 구성

ECS는 AWS의 컨테이너 오케스트레이션 서비스이다. 컨테이너를 Task로 실행하고 Service가 원하는 개수를 유지한다.

ClusterECS 작업이 실행되는 논리적 공간
Task Definition컨테이너 실행 설정
Task실제로 실행 중인 컨테이너 단위
ServiceTask 개수 유지와 ALB 연결
ALB ↓ Target Group ↓ ECS Service ↓ ECS Task ↓ Container

8. ECS Task Definition

Task Definition에는 이미지, CPU, 메모리, 포트, 환경변수, 로그 설정이 포함된다.

{
  "family": "skills-app",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "256",
  "memory": "512",
  "containerDefinitions": [
    {
      "name": "app",
      "image": "ACCOUNT_ID.dkr.ecr.ap-northeast-2.amazonaws.com/myapp:latest",
      "portMappings": [
        { "containerPort": 8080, "protocol": "tcp" }
      ],
      "essential": true,
      "logConfiguration": {
        "logDriver": "awslogs",
        "options": {
          "awslogs-group": "/ecs/skills-app",
          "awslogs-region": "ap-northeast-2",
          "awslogs-stream-prefix": "ecs"
        }
      }
    }
  ]
}
Task Definition의 containerPort와 ALB Target Group의 port가 일치해야 한다.

9. Task Role과 Execution Role

구분역할대표 권한
Task Execution RoleECS가 컨테이너 실행에 필요한 권한ECR Pull, CloudWatch Logs
Task Role애플리케이션 코드가 AWS 서비스에 접근하는 권한S3, DynamoDB, SQS 접근
CannotPullContainerError는 Task Execution Role 권한, ECR 이미지 주소, NAT/인터넷 연결 문제를 확인해야 한다.

10. Fargate 네트워크 구성

Fargate는 서버 관리 없이 컨테이너를 실행할 수 있는 방식이다. awsvpc 네트워크 모드를 사용하므로 각 Task가 ENI와 Security Group을 가진다.

항목설명
SubnetTask가 실행될 Subnet. Private Subnet 권장
Security GroupALB에서 App Port로 접근 허용
Assign Public IPPublic Subnet 직접 실행 시 필요. Private Subnet이면 NAT 필요
NAT GatewayPrivate Task가 ECR Pull, 외부 API 호출 시 필요

11. ECS + ALB Health Check

ALB는 Target Group의 Health Check 결과를 기반으로 정상 Task에만 트래픽을 전달한다.

resource "aws_lb_target_group" "app" {
  port        = 8080
  protocol    = "HTTP"
  target_type = "ip"
  vpc_id      = aws_vpc.main.id

  health_check {
    path                = "/health"
    matcher             = "200"
    interval            = 30
    healthy_threshold   = 2
    unhealthy_threshold = 3
  }
}

ALB Unhealthy 대표 원인

  • Health Check Path가 실제 앱에 없음
  • 앱은 5000번 포트인데 Target Group은 8080으로 설정
  • ALB SG에서 ECS SG로 접근 불가
  • 앱이 시작되기 전에 Health Check가 실패
  • 환경변수 누락으로 앱이 Crash

12. Terraform ECS 구성 핵심

resource "aws_ecs_cluster" "main" {
  name = "skills-cluster"
}

resource "aws_cloudwatch_log_group" "app" {
  name              = "/ecs/skills-app"
  retention_in_days = 7
}

resource "aws_ecs_service" "app" {
  name            = "skills-app-service"
  cluster         = aws_ecs_cluster.main.id
  task_definition = aws_ecs_task_definition.app.arn
  desired_count   = 2
  launch_type     = "FARGATE"

  network_configuration {
    subnets         = [aws_subnet.private_a.id, aws_subnet.private_b.id]
    security_groups = [aws_security_group.ecs.id]
  }

  load_balancer {
    target_group_arn = aws_lb_target_group.app.arn
    container_name   = "app"
    container_port   = 8080
  }
}
ECS Service와 Target Group을 연결할 때 container_name과 container_port가 Task Definition과 정확히 일치해야 한다.

13. ECS 장애 대응 플레이북

Task가 실행되지 않을 때

  • Task Definition image 주소가 올바른가?
  • ECR에 해당 tag가 존재하는가?
  • Task Execution Role에 ECR/CloudWatch 권한이 있는가?
  • Private Subnet이면 NAT Gateway가 있는가?
  • CPU/Memory 값이 Fargate 조합에 맞는가?

Task가 바로 종료될 때

  • CloudWatch Logs에서 앱 에러 확인
  • 환경변수 누락 확인
  • DB 접속 정보 확인
  • CMD/ENTRYPOINT 오류 확인

ALB 접속이 안 될 때

  • Target Group Healthy 상태 확인
  • ALB Listener가 Target Group으로 Forward하는가?
  • ALB SG 80/443 Inbound 허용 확인
  • ECS SG가 ALB SG에서 App Port를 허용하는가?

14. 기능경기 실전 체크리스트

  • Dockerfile이 정상 빌드되는가?
  • 로컬에서 docker run으로 앱이 실행되는가?
  • ECR login, tag, push가 완료되었는가?
  • Task Definition의 이미지 주소가 최신인가?
  • Execution Role과 Task Role을 구분했는가?
  • CloudWatch Log Group이 설정되어 있는가?
  • ALB Target Group Health Check가 통과하는가?
  • Security Group이 ALB → ECS 방향으로 연결되어 있는가?
