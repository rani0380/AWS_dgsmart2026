1. AWS 네트워크가 중요한 이유

기능경기대회 클라우드컴퓨팅 문제에서 네트워크는 거의 모든 서비스의 기반이다. VPC, Subnet, Route Table, Security Group, ALB 설정이 잘못되면 EC2, ECS, EKS, RDS가 모두 정상 동작하지 않는다.

VPCAWS 안에 만드는 독립 사설 네트워크
SubnetAZ 단위로 나누는 네트워크 영역
Route Table트래픽이 어디로 갈지 결정하는 경로표
Security Group인스턴스/서비스 단위 상태 저장 방화벽
실전에서는 “리소스는 만들어졌는데 접속이 안 됨” 문제가 가장 많다. 대부분 Route Table, SG, Subnet Association, Health Check 문제이다.

2. VPC 기본 설계

기능경기 실전에서는 일반적으로 하나의 VPC 안에 Public Subnet과 Private Subnet을 분리하여 구성한다.

VPC 10.0.0.0/16 ├─ Public Subnet A 10.0.1.0/24 → ALB, Bastion, NAT Gateway ├─ Public Subnet B 10.0.2.0/24 → ALB, NAT Gateway ├─ Private App A 10.0.11.0/24 → ECS/EKS Application ├─ Private App B 10.0.12.0/24 → ECS/EKS Application ├─ Private DB A 10.0.21.0/24 → RDS └─ Private DB B 10.0.22.0/24 → RDS
구분배치 리소스라우팅
Public SubnetALB, Bastion, NAT Gateway0.0.0.0/0 → Internet Gateway
Private App SubnetECS, EKS Worker Node, 내부 API0.0.0.0/0 → NAT Gateway
Private DB SubnetRDS, Aurora인터넷 직접 연결 없음
RDS를 Public Subnet에 배치하거나 DB Security Group을 0.0.0.0/0으로 열면 보안 설계 감점 요소가 될 수 있다.

3. CIDR와 Subnet 크기

CIDR는 네트워크 주소 범위를 표현하는 방식이다. 기능경기에서는 계산을 복잡하게 하기보다 안정적인 범위를 사용하는 것이 좋다.

예시의미실전 사용
10.0.0.0/16큰 VPC 범위VPC 전체
10.0.1.0/24256개 IP 범위일반 Subnet
/28작은 범위EKS에는 비추천

AWS는 각 Subnet마다 5개의 IP를 예약한다. 따라서 /24 Subnet은 256개 중 실제 사용 가능 IP가 251개이다.

EKS는 Pod마다 IP를 사용하므로 Subnet을 너무 작게 만들면 Pod 생성 실패가 발생한다. 실전에서는 /24 이상을 권장한다.

4. Route Table, IGW, NAT Gateway

Public Route

Destination     Target
10.0.0.0/16     local
0.0.0.0/0       Internet Gateway

Private Route

Destination     Target
10.0.0.0/16     local
0.0.0.0/0       NAT Gateway

Terraform 예시

resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_support   = true
  enable_dns_hostnames = true
}

resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id
}

resource "aws_route" "public_internet" {
  route_table_id         = aws_route_table.public.id
  destination_cidr_block = "0.0.0.0/0"
  gateway_id             = aws_internet_gateway.main.id
}
Route Table을 만들고 Subnet Association을 하지 않으면 해당 Subnet은 의도한 Route Table을 사용하지 않는다.

권장 Security Group 설계

Internet ↓ 80/443 ALB Security Group ↓ 8080 App Security Group ↓ 3306 DB Security Group
# DB SG 예시: App SG에서만 MySQL 접근 허용
ingress {
  from_port       = 3306

기능경기에서 접속 장애의 70% 이상은 Security Group 또는 Route Table 문제로 발생한다.

6. DNS와 Route 53

DNS는 도메인 이름을 IP 주소 또는 AWS 리소스 주소로 변환한다. AWS에서는 Route 53을 사용하여 ALB, CloudFront, S3 정적 웹사이트 등에 도메인을 연결할 수 있다.

레코드용도
A도메인을 IPv4 주소로 연결
CNAME도메인을 다른 도메인으로 연결
AliasALB, CloudFront 등 AWS 리소스에 직접 연결
MX메일 서버 지정
resource "aws_route53_record" "app" {
  zone_id = aws_route53_zone.main.zone_id
  name    = "app"
  type    = "A"

  alias {
    name                   = aws_lb.main.dns_name
    zone_id                = aws_lb.main.zone_id
    evaluate_target_health = true
  }
}

7. Load Balancer 실전

로드밸런서는 외부 트래픽을 여러 대상에게 분산한다. 기능경기에서는 대부분 ALB(Application Load Balancer)가 사용된다.

구분ALBNLB
계층Layer 7Layer 4
프로토콜HTTP/HTTPSTCP/UDP
기능Path/Host Routing고성능 TCP 처리
대회 사용매우 자주고급 문제

ALB 구조

Client ↓ Application Load Balancer ↓ Listener : 80/443 ↓ Target Group : /health ↓ EC2 / ECS Task / EKS Pod

Target Group Health Check

resource "aws_lb_target_group" "app" {
  port     = 8080
  protocol = "HTTP"
  vpc_id   = aws_vpc.main.id

  health_check {
    path                = "/health"
    healthy_threshold   = 2
    unhealthy_threshold = 3
  }
}
ALB 502 또는 unhealthy 상태는 포트 불일치, health check path 오류, SG 미허용, 앱 실행 실패가 대표 원인이다.

8. EKS 네트워크 핵심

EKS는 AWS VPC CNI를 사용한다. Pod가 VPC의 IP를 직접 할당받기 때문에 Subnet IP 여유가 매우 중요하다.

Pod IPVPC Subnet에서 IP를 할당받음
Node ENIWorker Node의 ENI에 Pod IP가 연결됨
IP 부족Pod Pending 또는 IP 할당 실패 발생
kubectl describe pod POD_NAME
kubectl get nodes
kubectl get pods -A
EKS에서 Pod가 Pending인데 CPU/Memory 문제가 아니라면 Subnet IP 부족 또는 CNI 문제를 의심해야 한다.

9. VPC Peering과 Client VPN

VPC Peering은 서로 다른 VPC를 연결하는 기능이고, Client VPN은 외부 사용자가 Private VPC에 안전하게 접속하기 위한 기능이다.

VPC PeeringHub VPC와 App VPC 연결. 양쪽 Route Table 설정 필수
Transit Gateway여러 VPC를 중앙에서 연결하는 고급 네트워크 허브
Client VPN사용자 PC에서 Private Subnet 접속. 인증서와 Authorization Rule 필요
Peering 연결만 만들고 Route Table에 상대 VPC CIDR을 추가하지 않으면 통신되지 않는다.

10. 기능경기 실전 장애 대응 체크리스트

인터넷 접속이 안 될 때

  • Public IP가 있는가?
  • IGW가 VPC에 연결되어 있는가?
  • Route Table에 0.0.0.0/0 → IGW가 있는가?
  • Subnet Association이 되어 있는가?
  • Security Group inbound가 열려 있는가?

Private Subnet에서 외부로 나가지 못할 때

  • NAT Gateway가 Public Subnet에 있는가?
  • NAT Gateway에 Elastic IP가 연결되어 있는가?
  • Private Route Table에 0.0.0.0/0 → NAT Gateway가 있는가?

ALB가 unhealthy일 때

  • Target port와 앱 port가 일치하는가?
  • Health check path가 실제 존재하는가?
  • ALB SG에서 App SG로 접근 가능한가?
  • 앱 컨테이너/Pod가 정상 실행 중인가?
