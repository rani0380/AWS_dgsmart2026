1. 데이터베이스가 중요한 이유

클라우드 서비스는 대부분 데이터를 저장하고 조회한다. 기능경기대회에서는 웹 애플리케이션, API 서버, 메시지 시스템, 채팅 시스템, 회원 관리 시스템 등의 과제에서 RDS, Aurora, DynamoDB가 자주 사용된다.

RDSMySQL, PostgreSQL 등 관계형 데이터베이스를 관리형으로 제공
AuroraAWS 최적화 고성능 관계형 데이터베이스
DynamoDB서버리스 NoSQL Key-Value/Document 데이터베이스
DAXDynamoDB 읽기 성능 향상을 위한 인메모리 캐시
DB가 정상이어도 네트워크, Security Group, IAM, 애플리케이션 환경변수가 잘못되면 서비스는 실패한다.

2. 관계형 DB와 NoSQL 비교

구분관계형 DBNoSQL
대표 서비스RDS, AuroraDynamoDB
데이터 구조Table, Row, ColumnItem, Attribute
질의 방식SQLKey 기반 조회, Query, Scan
장점정합성, 조인, 트랜잭션확장성, 서버리스, 높은 처리량
주의점Connection, Index, Lock 관리Partition Key 설계 중요
회원, 주문, 결제처럼 관계와 정합성이 중요한 데이터는 RDS/Aurora가 적합하고, 메시지, 로그, 이벤트처럼 빠른 읽기/쓰기가 중요한 데이터는 DynamoDB가 적합하다.

3. Amazon RDS 핵심

RDS는 AWS가 운영체제, DB 엔진 설치, 백업, 패치, 장애 조치 등을 관리하는 관계형 데이터베이스 서비스이다.

DB Instance실제 데이터베이스 서버
DB Subnet GroupRDS가 배치될 Subnet 묶음
Parameter GroupDB 엔진 설정값 관리
Option GroupDB 엔진별 추가 기능 관리

Terraform 예시: RDS MySQL

resource "aws_db_subnet_group" "main" {
  name = "skills-db-subnet"
  subnet_ids = [
    aws_subnet.db_a.id,
    aws_subnet.db_b.id
  ]
}

resource "aws_db_instance" "main" {
  identifier          = "skills-db"
  engine              = "mysql"
  engine_version      = "8.0"
  instance_class      = "db.t3.micro"
  allocated_storage   = 20
  db_subnet_group_name = aws_db_subnet_group.main.name
  vpc_security_group_ids = [aws_security_group.db.id]
  username            = var.db_username
  password            = var.db_password
  skip_final_snapshot = true
}
실전 과제에서는 편의를 위해 skip_final_snapshot = true를 쓰기도 하지만, 운영 환경에서는 데이터 손실 위험이 있으므로 신중해야 한다.

4. DB Subnet Group과 Security Group

RDS는 일반적으로 Private Subnet에 배치한다. DB Subnet Group은 RDS가 어느 Subnet에 생성될지 지정하는 리소스이다.

항목권장 설계
Subnet서로 다른 AZ의 Private DB Subnet 2개 이상
Public Accessfalse 권장
InboundApp Security Group에서만 DB Port 허용
DB PortMySQL 3306, PostgreSQL 5432
resource "aws_security_group" "db" {
  name   = "skills-db-sg"
  vpc_id = aws_vpc.main.id

  ingress {
    from_port       = 3306
    to_port         = 3306
    protocol        = "tcp"
    security_groups = [aws_security_group.app.id]
  }
}
DB Security Group은 CIDR보다 App Security Group을 Source로 지정하는 것이 안전하고 실무적이다.

5. Multi-AZ와 Read Replica

구분목적특징
Multi-AZ고가용성Standby DB 자동 장애 조치
Read Replica읽기 부하 분산비동기 복제, 읽기 전용
Multi-AZ Primary DB ──동기 복제── Standby DB 장애 발생 시 자동 Failover Read Replica Primary DB ──비동기 복제── Read Replica 조회 트래픽 분산
Read Replica는 읽기 전용이므로 쓰기 작업을 보내면 오류가 발생한다.

6. Amazon Aurora

Aurora는 MySQL/PostgreSQL과 호환되는 AWS 최적화 관계형 데이터베이스이다. 일반 RDS보다 고성능, 빠른 장애 조치, 자동 스토리지 확장이 강점이다.

Writer Endpoint쓰기 작업용 엔드포인트
Reader Endpoint읽기 작업용 엔드포인트
Shared Storage여러 인스턴스가 공유하는 분산 스토리지
resource "aws_rds_cluster" "main" {
  cluster_identifier = "skills-aurora"
  engine             = "aurora-mysql"
  database_name      = "skills"
  master_username    = var.db_username
  master_password    = var.db_password
  db_subnet_group_name = aws_db_subnet_group.main.name
  vpc_security_group_ids = [aws_security_group.db.id]
  skip_final_snapshot = true
}
Aurora를 사용할 때 애플리케이션은 쓰기 작업에는 Writer Endpoint, 읽기 작업에는 Reader Endpoint를 사용하도록 분리할 수 있다.

7. DynamoDB 핵심

DynamoDB는 서버리스 NoSQL 데이터베이스이다. 서버 관리가 필요 없고, Key 설계에 따라 높은 성능을 낼 수 있다.

구성 요소설명
Partition Key데이터를 분산 저장하는 기준 키
Sort Key같은 Partition Key 안에서 정렬/범위 조회 기준
AttributeItem이 가지는 속성
Billing ModePAY_PER_REQUEST 또는 Provisioned

메시지 테이블 설계 예시

Table: messages Partition Key: room_id Sort Key: timestamp Attributes: user_id, message, created_at
resource "aws_dynamodb_table" "messages" {
  name         = "messages"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "room_id"
  range_key    = "timestamp"

  attribute {
    name = "room_id"
    type = "S"
  }

  attribute {
    name = "timestamp"
    type = "S"
  }
}
Partition Key가 특정 값에만 몰리면 Hot Partition이 발생하여 성능 저하와 Throttling이 발생할 수 있다.

8. DAX와 Lambda + DynamoDB 패턴

DAX는 DynamoDB Accelerator로, 읽기 요청이 많은 서비스에서 지연시간을 줄이기 위한 인메모리 캐시이다.

Client ↓ API Gateway ↓ Lambda ↓ DAX 또는 DynamoDB ↓ DynamoDB Table
API GatewayHTTP 요청 진입점
Lambda비즈니스 로직 실행
DynamoDB메시지/이벤트 저장
DAX읽기 성능 향상 캐시
기능경기 자동화 과제에서는 API Gateway + Lambda + DynamoDB 조합이 자주 사용된다.

9. 트랜잭션과 ACID

트랜잭션은 하나의 논리적 작업 단위이다. 예를 들어 계좌 이체는 출금과 입금이 모두 성공해야 한다.

ACID의미설명
Atomicity원자성전부 성공 또는 전부 실패
Consistency일관성트랜잭션 전후 데이터 규칙 유지
Isolation격리성동시 트랜잭션 간 간섭 제어
Durability지속성커밋된 데이터는 장애 후에도 보존

Deadlock 예시

Tx1: Row A Lock 획득 → Row B 대기 Tx2: Row B Lock 획득 → Row A 대기 결과: 서로 기다리며 Deadlock 발생

10. DB 장애 대응

DB 접속 안 됨

  • DB Endpoint가 올바른가?
  • DB Port가 맞는가? MySQL 3306, PostgreSQL 5432
  • App SG에서 DB SG로 Inbound가 열려 있는가?
  • DB가 Private Subnet에 있고 App도 접근 가능한 경로에 있는가?
  • 사용자명/비밀번호/DB 이름이 맞는가?

Too many connections

  • Connection Pool을 사용하는가?
  • 애플리케이션이 연결을 닫고 있는가?
  • DatabaseConnections 지표가 급증했는가?

Slow Query

  • 인덱스가 있는가?
  • Full Table Scan이 발생하는가?
  • ORDER BY, GROUP BY가 인덱스를 활용하는가?
  • Slow Query Log를 확인했는가?

애플리케이션이 느릴 때 서버 CPU만 보지 말고 DB Connection, Slow Query, Lock, Latency를 함께 확인해야 한다.

12. 기능경기 실전 체크리스트

  • DB Subnet Group이 서로 다른 AZ의 Private Subnet으로 구성되었는가?
  • RDS publicly_accessible이 불필요하게 true가 아닌가?
  • DB Security Group이 App Security Group에서만 접근 가능하도록 구성되었는가?
  • 환경변수 DB_HOST, DB_USER, DB_PASSWORD, DB_NAME이 올바른가?
  • DynamoDB Partition Key와 Sort Key가 문제 요구사항과 일치하는가?
  • Lambda에서 DynamoDB 접근 IAM 권한이 있는가?
  • CloudWatch Logs에서 DB 연결 오류를 확인했는가?
