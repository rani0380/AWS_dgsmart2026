1. Linux가 기능경기에서 중요한 이유

클라우드컴퓨팅 직종에서 사용하는 EC2, ECS 컨테이너 런타임, EKS Worker Node는 대부분 Linux 기반으로 동작한다. 따라서 AWS Console이나 Terraform으로 리소스를 만들 수 있더라도, 서버 안에서 무슨 일이 발생하는지 확인하지 못하면 장애 대응이 어렵다.

EC2SSH 접속, 서비스 실행, 포트 확인, 로그 분석이 필요함
ECSDocker 이미지 실행, CloudWatch Logs, Task 재시작 원인 분석 필요
EKSkubelet, container runtime, Pod 상태를 Linux 관점에서 이해해야 함
대회 실전에서는 “왜 안 되지?”라고 추측하지 말고 Linux 명령어로 상태를 확인하는 습관이 중요함.

2. 프로세스와 데몬

프로세스는 실행 중인 프로그램이며, 데몬은 백그라운드에서 지속적으로 실행되는 시스템 서비스이다. 클라우드 환경에서는 sshd, dockerd, containerd, kubelet, nginx 등이 대표적이다.

구분설명예시
프로세스실행 중인 프로그램python app.py, nginx
데몬백그라운드 서비스sshd, dockerd, kubelet
PID 1컨테이너 내부의 메인 프로세스컨테이너 종료와 직접 관련

필수 명령어

ps aux
ps -ef
top
systemctl status docker
systemctl restart docker
systemctl status kubelet
EKS Node에서 Pod가 뜨지 않을 때 kubelet 상태가 비정상인 경우가 있다. kubectl만 보지 말고 Node 내부 서비스도 확인해야 한다.

3. CPU, 메모리, 디스크 확인

서비스 장애의 상당수는 애플리케이션 코드 문제가 아니라 서버 자원 부족에서 발생한다.

CPUtop, htop으로 사용률과 부하 확인
Memoryfree -h, OOMKilled 원인 확인
Diskdf -h, Docker 이미지와 로그로 인한 용량 부족 확인
Portss -tlnp로 LISTEN 포트와 충돌 확인
top
free -h
df -h
df -i
ss -tlnp

실전 예시: Docker Pull 실패

# 디스크 확인
df -h

# Docker 사용량 확인
docker system df

# 사용하지 않는 이미지/컨테이너 정리
docker system prune -a

4. 로그 확인

장애 대응의 첫 번째 근거는 로그이다. 기능경기에서는 빠르게 로그 위치를 찾는 능력이 중요하다.

대상명령어확인 내용
Linux 서비스journalctl -xe시스템 서비스 오류
Dockerdocker logs 컨테이너컨테이너 앱 로그
Kuberneteskubectl logs podPod 로그
ECSCloudWatch LogsTask 실행 로그
journalctl -xe
journalctl -u docker

docker ps -a
docker logs CONTAINER_ID

kubectl logs POD_NAME -f
kubectl describe pod POD_NAME
로그를 볼 때는 에러 메시지, 포트, 환경변수, DB 연결, 권한 문제를 우선 확인함.

5. 기능경기 실전 장애 대응 체크리스트

  • SSH 접속 가능 여부 확인
  • CPU 사용률 확인: top
  • 메모리 부족 확인: free -h
  • 디스크 부족 확인: df -h
  • 포트 충돌 확인: ss -tlnp
  • Docker daemon 상태 확인: systemctl status docker
  • 컨테이너 로그 확인: docker logs
  • EKS Node라면 kubelet 상태 확인
  • 보안그룹과 OS 방화벽 구분

6. 출제 예상 포인트

쉬운 난이도EC2 접속, 패키지 설치, 포트 확인, 서비스 실행
중간 난이도Docker daemon 오류, 로그 확인, 앱 재시작
고급 난이도OOM, disk full, kubelet 문제, zombie process
Linux는 별도 과목처럼 보이지만 AWS/ECS/EKS 모든 문제의 기반이므로 반드시 익숙해져야 함.
