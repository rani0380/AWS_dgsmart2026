1. EKS가 중요한 이유

Amazon EKS는 AWS에서 제공하는 관리형 Kubernetes 서비스이다. 기능경기에서는 컨테이너 애플리케이션을 Kubernetes 방식으로 배포하고, Service와 Ingress를 통해 외부에 노출하며, 장애 원인을 kubectl로 분석하는 능력이 중요하다.

Control PlaneAPI Server, Scheduler, Controller, etcd는 AWS가 관리
Worker NodePod가 실제 실행되는 EC2 기반 노드
Pod컨테이너 실행의 최소 단위
IngressALB와 연동해 HTTP/HTTPS 트래픽을 라우팅
EKS 문제는 리소스 생성보다 kubectl로 상태를 확인하고 원인을 찾는 과정이 더 중요하다.

2. kubectl 기본 명령어

kubectl cluster-info
kubectl get nodes
kubectl get pods -A
kubectl get all -n default
kubectl describe pod POD_NAME
kubectl logs POD_NAME -f
kubectl exec -it POD_NAME -- sh
kubectl get events --sort-by=.lastTimestamp
명령어확인 내용
get리소스 목록 확인
describe상세 상태와 이벤트 확인
logs컨테이너 로그 확인
execPod 내부 접속
events스케줄링, 이미지 Pull, Probe 실패 원인 확인

3. Namespace

Namespace는 하나의 클러스터를 논리적으로 분리하는 단위이다. 대회에서는 default, production, monitoring 같은 Namespace를 사용할 수 있다.

kubectl create namespace production
kubectl get ns
kubectl get pods -n production
kubectl get all --all-namespaces
리소스를 다른 Namespace에 생성해 놓고 default에서 조회하면 보이지 않는다. 항상 -n 옵션을 확인한다.

4. Deployment

Deployment는 Stateless 애플리케이션 배포의 기본 리소스이다. Pod 복제본 수를 유지하고 롤링 업데이트와 롤백을 제공한다.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: nginx:1.25
        ports:
        - containerPort: 80
        resources:
          requests:
            cpu: "100m"
            memory: "128Mi"
          limits:
            cpu: "500m"
            memory: "512Mi"

롤링 업데이트

kubectl set image deployment/web web=nginx:1.26
kubectl rollout status deployment/web
kubectl rollout history deployment/web
kubectl rollout undo deployment/web

5. Service

Pod는 생성과 삭제 과정에서 IP가 바뀐다. Service는 Pod 집합에 안정적인 접근 지점을 제공한다.

타입용도
ClusterIP클러스터 내부 통신
NodePort노드 포트로 외부 접근
LoadBalancerAWS ELB 자동 생성
ExternalName외부 DNS를 내부 Service처럼 사용
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  type: ClusterIP
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 80
Service selector와 Deployment label이 다르면 Endpoint가 생성되지 않아 통신되지 않는다.

6. Ingress와 ALB

Ingress는 HTTP/HTTPS 요청을 내부 Service로 라우팅한다. EKS에서는 AWS Load Balancer Controller를 사용하여 Ingress를 ALB로 연결한다.

Internet ↓ AWS ALB ↓ Ingress Rule ↓ Kubernetes Service ↓ Pod
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
spec:
  rules:
  - http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-svc
            port:
              number: 80
Ingress가 생성되어도 ALB가 안 생기면 AWS Load Balancer Controller, IAM 권한, Subnet Tag를 확인한다.

7. ConfigMap과 Secret

ConfigMap은 일반 설정값, Secret은 비밀번호나 토큰 같은 민감 정보를 저장한다.

kubectl create configmap app-config --from-literal=APP_ENV=production
kubectl create secret generic db-secret --from-literal=password=Password123
envFrom:
- configMapRef:
    name: app-config
- secretRef:
    name: db-secret
Kubernetes Secret은 기본적으로 base64 인코딩일 뿐 강력한 암호화가 아니다. 운영 환경에서는 KMS 연동을 고려한다.

8. Probe와 HPA

Probe는 Pod 상태를 점검하고, HPA는 부하에 따라 Pod 수를 자동 조절한다.

livenessProbe:
  httpGet:
    path: /health
    port: 8080
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
kubectl autoscale deployment web \
  --cpu-percent=70 \
  --min=2 \
  --max=10
Probe path나 port가 잘못되면 정상 앱도 계속 재시작될 수 있다.

9. EKS 네트워크와 IP 부족

AWS VPC CNI는 Pod에 VPC IP를 할당한다. Subnet IP가 부족하면 Pod가 Pending 상태에 머무르거나 IP 할당 실패 이벤트가 발생할 수 있다.

kubectl describe pod POD_NAME
kubectl get events --sort-by=.lastTimestamp
EKS용 Subnet을 /28처럼 작게 만들면 Pod IP 부족 문제가 쉽게 발생한다. 실전에서는 /24 이상을 권장한다.

10. 장애 대응 플레이북

Pending

  • Node 리소스 부족 확인
  • Taint/Toleration 확인
  • PVC 문제 확인
  • Subnet IP 부족 확인

CrashLoopBackOff

  • kubectl logs로 앱 오류 확인
  • 환경변수 누락 확인
  • DB 연결 정보 확인
  • CMD/ENTRYPOINT 확인

ImagePullBackOff

  • 이미지 이름과 태그 확인
  • ECR 권한 확인
  • Private Registry 인증 확인

Ingress/ALB 실패

  • AWS Load Balancer Controller 상태 확인
  • Ingress annotation 확인
  • Subnet Tag 확인
  • Target Group Health Check 확인

11. 기능경기 체크리스트

  • kubectl get nodes 결과가 Ready인가?
  • Deployment replicas가 원하는 수로 유지되는가?
  • Service selector와 Pod label이 일치하는가?
  • Ingress가 ALB를 생성했는가?
  • Pod logs에 오류가 없는가?
  • events에 ImagePull, Probe, Scheduling 오류가 없는가?
  • 외부 ALB URL로 정상 응답하는가?

12. 출제 예상 포인트

기본Deployment, Service, kubectl logs/describe
중급Ingress, ALB Controller, ConfigMap, Secret
고급HPA, IRSA, PVC, StatefulSet, Network Policy
EKS 문제의 최종 검증은 “Pod Running”이 아니라 “외부에서 애플리케이션이 정상 응답하는가”이다.
